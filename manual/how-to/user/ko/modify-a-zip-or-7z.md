# 기존 아카이브에서 엔트리를 추가, 교체 또는 제거하는 방법

수정은 하나의 세션으로 진행됩니다: `Archive::modify`로 아카이브를 열고, 핸들에 대해 변경 사항을 대기열에 추가한 다음, 커밋합니다. `commit_changes`가 실행될 때까지 디스크의 아카이브는 손대지 않은 상태로 유지되며, 커밋은 전체 재작성 후 원자적 교체로 이어집니다 — 이 구조의 근거에 대해서는 [수정 작업이 아카이브를 재작성하는 이유](../../../explanation/developer/ko/modification-is-a-rewrite.md)를 참조하세요.

## 전제 조건

- **포맷이 ZIP 또는 7z임.** `ArchiveFormat::can_modify`가 true인 유일한 두 포맷입니다. TAR 변형, ISO, 단독 압축 스트림 또는 RAR에 대해 `Archive::modify`를 호출하면 해당 포맷을 명시하는 이유와 함께 `OperationBlocked`로 실패합니다.
- **아카이브가 암호화되지 않음.** `Archive::modify`는 백엔드를 바인딩하기 전에 암호화 여부를 검사하고 "Encrypted archives cannot be modified"라는 이유로 암호화된 아카이브를 `OperationBlocked`로 거부합니다. 이 경로에는 비밀번호 매개변수가 없습니다.
- **아카이브가 존재하며 쓰기 가능함.** 세션은 파일 잠금을 획득하기 위해 파일-읽기쓰기 모드로 열립니다; 존재하지 않거나 쓰기 불가능한 경로는 `modify-lock-open`으로 라벨링된 `Io` 에러로 실패합니다.
- **다른 수정 세션이 해당 파일을 점유하지 않음** ([동시 세션](#동시-세션) 참조).
- **두 번째 복사본을 위한 공간.** 커밋은 원래 아카이브를 교체하기 전에 그 옆에 완전히 새로운 아카이브를 작성하며, 백업을 요청한 경우 또 다른 전체 복사본이 작성됩니다.

## 세션 열기

```rust
use unified_archive::Archive;

let mut archive = Archive::modify("release.zip")?;
```

핸들은 읽기 핸들의 역할도 겸합니다: `list_files`, `find_entry`, `find_entries`, `entry_count`, `is_solid` 모두 이 핸들에서 잘 작동합니다. 이들은 **디스크에 있는 그대로의** 아카이브를 설명합니다 — 엔트리 목록은 처음 사용 시 찍은 스냅샷이며 대기열에 추가된 변경 사항은 거기에 나타나지 않습니다.

커밋하지 않고 핸들을 drop하면 아카이브는 그대로 유지됩니다. 대기 중인 작업이 남아 있는 수정 핸들에 대해 `finish`나 `close`를 호출하면 작업들을 침묵 속에 버리는 대신 `OperationBlocked`로 거부됩니다; 대기열이 비어 있는 핸들은 조용히 닫힙니다.

## 옵션과 함께 열기

`ModificationOptions`는 세션의 명시적 선택(opt-in) 동작을 전달하며 커밋 시점이 아닌 열기 시점에 전달됩니다 (AD 0020은 `modify`의 시그니처를 변경하는 대신 형태가 유사한 생성자를 선택함).

```rust
use unified_archive::{Archive, ModificationOptions};

let options = ModificationOptions::new().with_backup(".bak");
let mut archive = Archive::modify_with_options("release.zip", options)?;
```

`ModificationOptions::new`의 기본값 (`Default`와 동일): `preserve_metadata: true`, `create_backup: false`, `backup_suffix: ".bak"`, `compression: None`.

- **`with_backup(suffix)`**는 백업을 켜고 접미사를 설정합니다. 백업은 항상 인접 파일인 `<archive path><suffix>`가 됩니다; 앞서 점이 없는 접미사에는 점이 추가됩니다. 빈 접미사나 `/` 또는 `\`를 포함하는 접미사는 무시되고 `.bak`이 대신 사용됩니다 — 디버그 빌드에서는 `debug_assert`가 발동하고, 릴리스 빌드에서는 치환이 침묵 속에 일어나며, 공용 필드를 직접 할당한 경우에 대비해 동일한 정제 작업이 커밋 시점에 다시 실행됩니다.
- **`without_metadata_preservation()`**은 `preserve_metadata`를 해제합니다.
- **`compression`**은 빌더가 없는 공개 필드입니다. `format`이 아카이브 자체의 포맷과 일치하는 `CompressionOptions`를 할당하세요; `level`과 `progress`는 재작성 시 반영됩니다. 일치하지 않는 `format`은 커밋 시 거부됩니다 — 재작성으로 컨테이너를 변경할 수는 없습니다. `password` 및 `split_size`는 `Archive::create` 파사드가 사용하는 것과 동일한 생성 시점 가드에 의해 거부됩니다.
- `ModificationOptions`는 `Clone`이 아닌데, `compression`에 진행률 콜백이 들어있을 수 있기 때문입니다. 세션당 새 값을 빌드하세요.

### 메타데이터 보존이 실제로 복원하는 항목

`preserve_metadata: true`의 경우, 유지된 **일반 파일** 엔트리는 소스 목록에 노출되었던 수정, 접근, 생성 시간과 Unix 권한 비트를 그대로 유지한 채 다시 출력됩니다. ZIP 라이터는 `0x5455` 확장 타임스탬프 엑스트라 필드에 접근 및 생성 시간을 기록하며; libarchive 라이터(7z에 사용됨)는 엔트리에 직접 이를 설정합니다. `add_entry_from_path`로 대기열에 추가된 엔트리는 디스크의 소스 파일에서 시간과 권한을 가져옵니다.

플래그에 관계없이 두 가지 항목은 백엔드 기본값으로 폴백됩니다:

- **유지된 디렉토리 엔트리**는 라이터의 기본 권한(libarchive 경로에서는 `0o755`)과 재작성 시점의 실제 시간을 받습니다.
- **바이트나 리더로부터 대기열에 추가된 엔트리**는 가져올 소스 메타데이터가 없으므로 라이터의 기본값이 적용됩니다.

아카이브 *파일* 자체는 별개의 문제입니다 — [커밋이 전달하지 않는 항목](#커밋이-전달하지-않는-항목)을 참조하세요.

## 변경 사항 대기열에 추가

이 모든 호출은 의도만 기록합니다. 아카이브 내부 경로를 즉시 검증하고, 빈 이름, NUL을 포함하는 이름, 선행 `./`, 어디에든 있는 `..` 세그먼트, 또는 절대/드라이브 접두사 경로에 대해 `InvalidPath`를 반환합니다 (해당 검사 전에 역슬래시는 슬래시로 정규화되므로 `..\..\evil` 역시 Unix에서도 거부됨). 검사는 이름을 `std::path::Components`로 읽어 선행 점을 제외한 모든 `.`을 정규화해 제거하므로 `a/./b`는 통과되어 적힌 대로 저장됩니다.

추가:

- `add_entry(path, data)` — 바이트를 대기열로 스냅샷합니다. 즉시 버퍼를 drop하거나 변경할 수 있습니다.
- `add_entry_from_path(archive_path, fs_path)` — 파일 시스템 경로만 기록합니다. 커밋 시점에 해당 경로를 열고 그 순간에 지정된 항목을 아카이브하므로, 커밋 전 작성된 동일 경로 교체본이 침묵 속에 반영됩니다. 대용량 파일에 사용해야 하는 호출입니다: 페이로드가 메모리에 버퍼링되지 않습니다.
- `add_entry_from_reader(archive_path, reader, size)` — 소유권 있는 `Read + Send + 'static` 소스를 받으므로 로컬 버퍼에서 빌려오는 리더는 컴파일되지 않습니다. `Some(n)`을 전달하면 길이가 사전에 선언되며 다른 수의 바이트를 전달하는 리더는 커밋 시 거부됩니다. `None`을 전달하면 리더를 임시 파일로 먼저 쏟아부어(drain) 길이를 알아냅니다; 해당 드레인은 기본 단일 파일 추출 제한(1 GiB)으로 한정되며 이를 초과하는 소스는 `OperationBlocked`로 실패합니다.
- `add_directory_entry(path)` — 내용이 없는 디렉토리 엔트리를 대기열에 추가합니다. 중복된 디렉토리 경로는 하나의 방출 레코드로 압축됩니다.

제거:

- `remove_entry(path)`는 소스 목록에 대해 경로를 확인하고 매칭되는 **모든** 엔트리를 표시하여 매칭된 개수를 반환합니다. ZIP과 7z 모두 중복 경로를 허용하므로 둘 이상이 될 수 있습니다. 매칭되는 항목이 없는 경로는 `Ok(0)`을 반환하며 에러가 아닙니다 — 엄격한 제거가 필요한 경우 개수를 확인하세요.
- `remove_entry_by_id(id)`는 `list_files()` 순서의 위치 인덱스로 정확히 하나의 엔트리를 표시합니다. 중복 경로가 존재할 때 정밀한 도구입니다. 범위를 벗어난 ID는 `OperationBlocked`입니다.

교체는 두 작업의 조합이며 추가와 동일한 인자 형식을 가집니다: `replace_entry(path, data)`, `replace_entry_from_path(path, fs_path)`, `replace_entry_from_reader(path, reader, size)`. 각각은 해당 경로의 모든 소스 엔트리를 제거하고 하나의 새 엔트리를 대기열에 추가합니다. 소스 아카이브에 해당 경로가 없었던 경우 제거 작업은 아무것도 매칭하지 않으며 추가는 여전히 실행됩니다 — 결과는 에러가 아닌 일반 추가입니다. 교체 실패 처리가 필요한 경우 `remove_entry`를 직접 호출하고 개수를 확인하세요.

제거는 오직 *소스* 엔트리만을 대상으로 한다는 점에 유의하세요. 한 세션에서 추가를 대기열에 넣고 동일한 경로를 제거해도 추가가 취소되지는 않습니다.

## 대기열 검사 및 폐기

```rust
let queued = archive.pending_operations()?;   // 추가 + 제거 + 디렉토리 엔트리
if queued > 0 {
    archive.clear_operations()?;              // 세 대기열 모두 폐기
}
```

`clear_operations`는 구체화하지 않고 대기열의 리더 소스를 포기하는 유일한 방법이며, 반드시 커밋 *전에* 사용해야 합니다 — `commit_changes`는 핸들을 값으로 가져가므로 커밋 실패 후에는 지울 수 있는 것이 남지 않습니다.

두 호출 모두 수정 모드가 아닌 핸들에서는 `OperationBlocked`를 반환합니다.

## 커밋

```rust
archive.commit_changes()?;
```

`commit_changes`는 핸들을 소비합니다. 순서대로 수행하는 작업:

1. 사전 쓰기 가드를 다시 실행합니다: 압축 오버라이드 검사, 유지되는 모든 엔트리 경로의 재검증, 중복 출력 경로 및 파일 대 디렉토리 충돌(`a` 대 `a/b`)을 거부하는 네임스페이스 검사, 그리고 ZIP의 경우 중앙 디렉토리에 대한 소스 목록 교차 검사.
2. 동일한 디렉토리에 동일한 포맷으로 `<archive path>.tmp.<pid>.<nanos>.<counter>` 위치에 새 아카이브를 생성합니다.
3. 유지된 모든 엔트리를 복사한 다음 대기열에 있던 디렉토리 엔트리, 그리고 대기열에 있던 추가 항목들을 복사합니다.
4. ZIP의 경우 아카이브 수준 주석 및 각 유지 엔트리의 저장/deflate 압축 방식을 이어받아 전달합니다.
5. 원래 아카이브의 Unix 권한 비트를 임시 파일에 복사하여 교체 시 접근 권한이 넓어지지 않도록 합니다.
6. 백업이 요청된 경우 원래 파일의 복사본을 만들어 둡니다. 백업 대상은 독점적으로 점유되므로 기존의 `<path>.bak`이 있으면 덮어쓰지 않고 "backup target already exists"라는 메시지와 함께 커밋에 실패합니다; 교체 전에 복사본이 디스크로 플러시됩니다.
7. 임시 파일의 이름을 원래 파일 위로 변경하고 상위 디렉토리에 대해 최선형(best-effort) 동기화를 수행합니다.

비어 있는 대기열은 단축 처리됩니다: `commit_changes`는 아무것도 재작성하지 않고 백업을 작성하지 않은 채 `Ok(())`를 반환합니다.

실패 시 임시 파일이 제거되고 원래 아카이브는 정확히 있던 상태로 남습니다 — 하지만 중복 출력 경로나 잘못된 백업 접미사와 같은 복구 가능한 거부의 경우에도 핸들은 사라집니다. 다시 시도하려면 새 `Archive::modify` 세션을 열고 다시 대기열에 넣으세요; 이전 세션의 잠금은 핸들이 drop될 때 해제되었습니다. 핸들을 위험에 빠뜨리지 않고 대기열을 테스트하려면 `v2-api` 기능의 `ModifyArchive`가 제공하는 `try_commit_changes`를 사용할 수 있으며, 이는 `&mut self`에 대해 동일한 가드를 실행합니다. 해당 성공을 스냅샷 시점에만 유효한 것으로 처리하세요: 임대를 보장하지 않으므로 실제 커밋 시 모든 가드가 다시 실행됩니다.

## 동시 세션

`Archive::modify`는 다른 작업을 수행하기 전에 아카이브에 대해 권고성 독점 잠금을 획득합니다 — 포맷 감지 전, 기능 검사 전, 암호화 검사 전에 획득합니다. 첫 번째 핸들이 살아있는 동안 동일한 경로에 대해 두 번째 `Archive::modify`를 실행하면 즉시 실패합니다:

```text
OperationBlocked { operation: "modify", reason: "Another Modify session holds the advisory lock on release.zip" }
```

이 실패는 우회해야 할 한계가 아니라 의도된 동작입니다. 하나의 파일에 대한 두 개의 동시 재작성 및 교체 세션은 각각 동일한 소스로부터 완전한 새 아카이브를 작성한 다음 그 위로 이름을 바꾸는 경합을 벌이게 됩니다; 패배자의 변경 사항은 어디에서도 에러 없이 사라집니다. 두 번째 `modify` 호출을 실패로 처리하면 침묵속 데이터 손실을 처리 가능한 에러로 변환해주며, 비동기(non-blocking) 획득 방식은 호출자가 대기, 건너뛰기, 보고 여부를 결정함을 의미합니다 — 데드락 위험이 없습니다 (MADR-0009). 핸들이 drop되면 잠금이 해제되므로 `modify`를 감싸는 재시도 루프는 타당한 패턴입니다.

잠금은 **권고성(advisory)**입니다: 이 라이브러리를 사용하는 프로세스들을 조율합니다. 동일한 경로를 작성하는 다른 모든 프로세스는 영향을 받지 않습니다. 세션은 추가적으로 열기 시점에 아카이브의 inode 식별자를 고정하고 경로를 다시 해석하는 각 단계 전마다 이를 다시 검사하므로, 협조하지 않는 라이터가 경로명을 교체해도 쫓아가지 않고 포착합니다 — [설명 페이지](../../../explanation/developer/ko/modification-is-a-rewrite.md)에서 이것이 보장하는 바와 보장하지 않는 바를 다룹니다.

## 커밋이 전달하지 않는 항목

재작성이 **새로운 inode**를 설치하기 때문에, 커밋이 명시적으로 다시 적용하는 항목만 아카이브 파일에 남습니다. 그것은 Unix 권한 비트이며 다른 것은 없습니다. 소유권(uid/gid), POSIX ACL, 확장 속성 및 보안 라벨, 그리고 아카이브 파일 자체의 타임스탬프는 모두 손실됩니다 — 교체된 파일은 재작성 시점의 실제 시간을 가집니다. `with_backup`으로 생성된 백업도 동일한 계약을 따릅니다. 커밋이 반환된 후 워크플로우가 의존하는 모든 항목을 다시 적용하세요.

아카이브 내부에서 재작성은 두 가지 방식으로 의도적인 손실이 발생합니다:

- **소스의 심볼릭 링크, 하드 링크 및 기타 특수 엔트리는 삭제됩니다.** 새 컨테이너로 복사되지 않으며 에러가 발생하지도 않습니다; 결과 아카이브는 단순히 더 적은 엔트리를 가집니다. 이러한 엔트리는 출력에서 이름을 주장하지 않으므로 동일한 세션에서 삭제된 링크 경로에 일반 파일을 추가하는 것은 정당합니다.
- **7z 솔리드 블록 레이아웃은 재현되지 않습니다.** 새 아카이브는 일반 생성 라이터로 작성되므로 블록 그룹화 및 7z 전용 메타데이터가 재생성됩니다. 두 포맷 모두 정확히 이를 알리기 위해 수정을 `Support::Partial`로 보고합니다.

## 기타 경계 사항

- **파일 시스템 심볼릭 링크는 콘텐츠로 대기열에 추가될 수 없습니다.** `add_entry_from_path`는 이의 없이 경로를 수용하지만, 커밋 시 라이터는 심볼릭 링크 소스를 `OperationBlocked`로 아카이브하기를 거부합니다. 직접 링크를 해제하고 대상을 전달하세요.
- **재암호화 불가.** 암호화된 아카이브는 `modify` 시점에 거부되므로 재작성을 거쳐 암호화를 유지하는 문제는 발생하지 않습니다. 수정 세션에서 암호화된 아카이브를 생성할 방법은 없습니다.
- **컨테이너 포맷은 고정됨.** `format`이 아카이브와 다른 압축 오버라이드는 해당 경로에 다른 컨테이너를 침묵 속에 작성하는 대신 커밋 시 거부됩니다.
- **크래시 복구 저널 없음.** 영속성은 임시 파일과 원자적 이름 변경에 의존합니다. 재작성 중간에 크래시가 발생하면 원본은 온전하게 유지되고 그 옆에 식별 가능한 `.tmp.<pid>.…` 파일이 남게 되며, 이를 자동으로 정리해 주지는 않습니다.

`examples/modify_archive.rs`는 추가, 제거 및 교체 흐름의 실행 가능한 엔드 투 엔드 버전입니다.
